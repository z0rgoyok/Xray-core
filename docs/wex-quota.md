# Управляемая квота VLESS для WEX

Опциональный механизм ограничивает оплаченный транспорт Happ. Существующие
пилотные пользователи сохраняют прежнее поведение. Включение требует
`WEX_QUOTA_DIR` с заранее инициализированным журналом; email оплаченных
credentials имеет префикс `wex-paid:`. При отсутствии или повреждении журнала
такие credentials получают отказ. Автоматического создания пустой базы нет.

## Учет и активные соединения

Учитывается сумма принятого для передачи payload в обоих направлениях. Перед
каждым вызовом записи размер блока фиксируется в append-only журнале, затем
выполняется `fsync`. Только после успешной синхронизации разрешается передача.
При ошибке записи/синхронизации оплаченные соединения закрываются. Пакет имеет
общий счетчик `packageId + periodId`; смена credential его сохраняет.

Вверх учет происходит непосредственно перед записью outbound `freedom`.
Вниз — перед записью декодированного тела VLESS клиенту. Для обычных TCP/UDP
протокольные заголовки исключены. Для VLESS Mux в нисходящем направлении
учитываются также заголовки Mux. Платная маршрутизация разрешает `freedom` и
`blackhole`, поэтому подмена outbound не дает обойти исходящий счетчик.
Splice для оплаченных исходящих соединений выключен. Штатный XHTTP multiplexing
сохраняется; перенос process-global XUDP pipe между платными соединениями
отключен. Иначе общий GlobalID мог присоединить платного пользователя к трубе
пилота либо прежнего credential.

Каждая передача удерживает билет до окончания вызова записи. На пакет доступно
128 билетов, каждый блок ограничен 64 КиБ. Дополнительные соединения ожидают
билет с отменой по контексту. Отдельного ограничения на число устройств или
потоков здесь нет. Одновременно предварительно учтенные незавершенные вызовы
составляют максимум 8 МиБ на пакет в обоих направлениях суммарно. При аварии
их расход сохраняется консервативно. Повторные аварии могут суммировать такой
расход. Это граница незавершенных вызовов записи; ОС и промежуточные протоколы
могут сохранять уже принятые буферы, поэтому доставку конечному сайту этот
счетчик не удостоверяет.

Квота не превышается. TCP допускает только остаток бюджета. UDP допускает
целую датаграмму либо получает отказ; небольшой остаток может остаться
неиспользованным. Новая авторизация передачи проверяет текущую политику и время
после `fsync`. Конечный срок ограничивает deadline записи; sweep каждые 10 мс
закрывает истекшие соединения. Байты, ранее принятые сетью, могут доставляться
позже конечного срока. При отзыве ACK возвращается после отмены контекстов и
закрытия соответствующих соединений. Чужие credentials сохраняются.

## Управление и контракт

Оператор явно выполняет offline `xray wexquota-init /absolute/private/path` и
регистрирует возвращенный несекретный `ledgerId` в защищенной конфигурации API.
Повторная инициализация существующего журнала запрещена. Каталог должен быть
приватным. В нем находятся `ledger.jsonl`, `ledger.lock` и `control.sock` 0600.

После запуска механизм остается разоруженным до сверки с backend. Приватный
Unix HTTP socket принимает:

```json
{
  "revision": 1,
  "expectedLedgerId": "зарегистрированный-id",
  "minSequence": 0,
  "grants": [{
    "email": "wex-paid:credential-id",
    "packageId": "happ-user-id",
    "periodId": "2026-10-10T12:00:00.000Z",
    "startsAt": "2026-10-10T12:00:00.000Z",
    "endsAt": "2026-11-10T12:00:00.000Z",
    "limitBytes": 30000000000
  }],
  "floors": [{
    "packageId": "happ-user-id",
    "periodId": "2026-10-10T12:00:00.000Z",
    "usedBytes": 0
  }]
}
```

`PUT /v1/grants` принимает полный снимок. `GET /v1/state` и успешный PUT
возвращают `ledgerId`, `sequence`, `revision`, `usage` (тот же формат floors),
`activeFlows`, `healthy`, `observedAt` в ISO UTC с миллисекундами. UUID доступа
в этом API отсутствует. `POST /v1/disarm` без тела закрывает оплаченные потоки
и разоружает механизм без изменения revision/расхода; повторный внешний Apply
требуется для возобновления. Это путь отказа при частичной синхронизации Handler API. Неизвестные поля и хвост после JSON отвергаются.

Revision монотонна; повтор той же revision требует идентичные grants.
Floors могут независимо повышать сохраненный расход. Уменьшение расхода
игнорируется. Неизвестный нулевой floor инертен; неизвестный положительный
floor требует отдельной сверки и получает отказ. Чужой ledgerId или sequence
ниже внешнего highwater разоружает оплаченный транспорт. Смена limit существующего
bucket запрещена. Period и его границы рассчитывает backend по принятой первой
выдаче Happ; runtime не выводит их из оплаты самостоятельно.

Backend сохраняет ledgerId, sequence и расход до выдачи пользователю подтверждения.
Перенос: сначала полный grant-снимок без прежнего email и с новым email в том же
bucket; после ACK — установка нового UUID через HandlerService. Старый UUID
уже блокируется quota hook, даже пока validator еще содержит его запись.
Удаление старой записи и проверка нового набора завершают синхронизацию.

HandlerService тоже требует приватного транспорта. `api.listen` поддерживает
`unix:///absolute/private/path/handler.sock`; родительский каталог должен иметь
0700, сокет получает 0600. Стандартный клиент `xray api --server=unix:///...`
использует этот socket. TCP API без аутентификации не подходит: локальный
пользователь мог бы создать credential без оплаченного префикса.

## Журнал и восстановление

Один writer удерживает flock отдельного lock-файла. Запись содержит SHA-256 и
монотонную sequence. После 4096 записей полное состояние записывается во временный
файл, синхронизируется, атомарно заменяет журнал, синхронизируется каталог,
затем открывается новый append descriptor. Начальный snapshot компактации
сохраняет sequence. Во время замены другие записи удерживаются mutex.

Неполный последний хвост обрезается до последнего полного события: такой хвост
не мог получить разрешение на forwarding. Повреждение полного события,
пропуск sequence или уменьшение расхода приводят к отказу. Перезапуск читает
сохраненный расход, затем требует внешней сверки highwater перед открытием доступа.

Восстановление произвольно старых копий всей ноды и backend невозможно определить
из их собственных файлов. Backup обязан согласовывать свежий runtime report с
внешним durable highwater. Если актуальность копии неизвестна, оплаченный транспорт
остается закрытым до восстановления последнего подтвержденного состояния или
операторской консервативной сверки. Повторная инициализация не является восстановлением.

## Проверка и ограничения производительности

`go test ./common/wexquota ./transport/internet/splithttp ./common/mux
./app/dispatcher ./proxy/freedom ./proxy/vless/inbound ./app/commander` проверяет
журнал, параллельный hard cap, отсутствие flow cap, transfer, expiry, failed fsync,
хвост, checksum/sequence, компактацию, floors и отмену застрявшего XHTTP Write.

`WEX_QUOTA_BINARY=/absolute/path/xray python3 -B testing/wexquota/runtime-fixture.py`
запускает исключительно loopback TCP/UDP/XHTTP, выдуманные UUID и временный ledger.
Проверяются полезный трафик 1 МиБ вверх/вниз на 1/8/32 потоках, малая квота,
пилот, перенос, expiry, XUDP collision, Unix API, stalled XHTTP и kill/restart.
Ни production, ни системные proxy/маршруты не меняются.

На Mac Apple M4 Max одиночный 2 КиБ charge занимает около 4 мс, примерно
0.51 МБ/с. Адаптивные блоки при 1 МиБ transfers давали примерно 11 МиБ/с
суммарно; параллельная дисковая нагрузка снижала результат до 5.5 МиБ/с.
Это локальные измерения. Перед production необходимы отдельные измерения на
целевом диске, проверка CPU/RSS и доступного места. Синхронизация каждого
блока ограничивает масштабирование; group commit допустим только при ожидании
каждым блоком успешного fsync его sequence перед передачей.
